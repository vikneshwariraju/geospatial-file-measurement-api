# Geospatial File Measurement API

A FastAPI backend that accepts geospatial files (KML and zipped Shapefiles), reads their features, converts geographic coordinates to a suitable projected coordinate reference system (CRS), calculates geometry measurements, and stores the results in SQLite.

## Features

- Upload `.kml` files and `.zip` archives containing one Shapefile.
- Read feature names, geometry types, and feature IDs.
- Calculate polygon area in square metres (`m²`).
- Calculate LineString length in metres (`m`).
- Keep Point features without a measurement.
- Transform features from their source CRS to an estimated UTM CRS before measuring.
- Validate unsupported extensions, empty uploads, invalid ZIP files, ZIP files without a `.shp`, and ZIPs containing multiple Shapefiles.
- Store upload status and measurement results in SQLite.
- Retrieve uploaded-file metadata and per-feature measurements through REST endpoints.

## API endpoints

### `POST /api/files/`

Upload a KML file or a ZIP containing one Shapefile. In Swagger UI, choose the endpoint, click **Try it out**, select the file, and execute the request.

Example successful response:

```json
{
  "id": 8,
  "filename": "chennai_shapefile.zip",
  "status": "completed",
  "original_crs": "EPSG:4326",
  "projected_crs": "EPSG:32644",
  "measurements_saved": 1
}
```

The returned ID is generated by the database; the example ID is illustrative.

### `GET /api/files/{file_id}/`

Returns the uploaded file's metadata, processing status, CRS information, and measurement count.

Example:

```json
{
  "id": 8,
  "filename": "chennai_shapefile.zip",
  "status": "completed",
  "original_crs": "EPSG:4326",
  "projected_crs": "EPSG:32644",
  "measurements_count": 1
}
```

### `GET /api/files/{file_id}/measurements/`

Returns each feature's geometry type, measurement type, measurement value, unit, and status.

Example Polygon measurement:

```json
{
  "feature_id": 0,
  "name": "Lake A",
  "geometry_type": "Polygon",
  "measurement_type": "area",
  "value": 1199020.1408400289,
  "unit": "m²",
  "status": "success"
}
```

### Error handling

The API rejects unsupported file extensions and empty uploads. Invalid ZIP archives, ZIPs without a `.shp`, ZIPs containing multiple Shapefiles, empty datasets, or files without a CRS are reported as processing/validation errors. A failed processing record is marked `failed` when a database record has already been created.

## Geometry and CRS handling

- **Polygon:** calculate area after reprojection; unit is square metres (`m²`).
- **LineString:** calculate length after reprojection; unit is metres (`m`).
- **Point:** no area or length is calculated, so the measurement fields are `null`.
- **Other geometry types:** keep the feature and mark its measurement status as `unsupported`.
- **CRS:** geographic coordinates such as EPSG:4326 use angular degrees, not metres. The processor estimates a suitable UTM CRS and reprojects the GeoDataFrame before calculating area or length. The selected CRS is returned in the API response.

## Run tests

From the project root, with the virtual environment activated:

```powershell
python -m pytest -v
```

The included tests use a temporary SQLite database and mock file parsing for endpoint tests, so they test API validation, persistence, status, retrieval, and geometry measurement logic without modifying the normal local database. They are not a substitute for manually testing real KML and Shapefile ZIP files through Swagger UI.

## Design decisions and limitations

- FastAPI provides REST endpoints and interactive OpenAPI documentation.
- GeoPandas handles geospatial file reading and CRS conversion.
- SQLAlchemy models uploaded files and per-feature measurements.
- SQLite keeps local setup simple for an assignment/demo.
- One Shapefile per ZIP is accepted to avoid ambiguous archive selection.
- Measurements are planar measurements in the estimated UTM CRS. For very large, cross-zone, polar, or otherwise unusual datasets, CRS selection should be reviewed rather than assuming one UTM CRS is suitable.
- The current processing endpoint is synchronous from the client's perspective. For large uploads, production hardening should include upload-size limits, safer archive extraction/validation, structured logging, and background processing.

## Example manual checks

1. Upload `sample.kml`; verify Point, LineString, and Polygon records.
2. Upload a ZIP containing a Point Shapefile.
3. Upload a ZIP containing a LineString Shapefile.
4. Upload a ZIP containing a Polygon Shapefile.
5. Try an unsupported file extension, an empty file, and a ZIP without a `.shp`.
6. Request a nonexistent file ID and confirm the API returns `404`.
